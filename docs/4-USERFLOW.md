# 사용자 흐름

> 상태: 기존 수동 흐름을 유지한다. 핵심 시나리오 서버·UI는 구현되어 표적 자동/컴포넌트 검증을 통과했다. 전체 테스트·타입 검사·린트·빌드는 통과했다. 브라우저 조작은 이 문서 확정 시점에 미검증이다 ([changes/014-core-scenarios.md](changes/014-core-scenarios.md)).

## 진입점과 종료점

- **진입**: 터미널에서 `npm run dev` → 브라우저로 `http://127.0.0.1:3000` 접속 → 프로젝트 목록. 앱 자체 계정 로그인은 없다.
- **종료**: 승인된 문서 세트를 zip으로 내려받는다. 이후 개발은 SDDMaker 밖에서 한다.

## 주요 여정

```text
프로젝트 목록
  └─ 새 프로젝트 (이름 + 아이디어 + 디자인 문서: 없으면 getdesign.md에서 골라 붙여넣기)
       └─ 프로젝트 상세
            ├─ 인터뷰 ──(요약 승인)──┐
            └─ 인터뷰 건너뛰기 ─────┤  (시작 전·도중 모두 가능)
                                     ▼
            0-PRODUCT ──(승인: 기능 목록 확정)──► 1-SYSTEM-ARCHITECTURE ► 3-DATABASE
                                     ▼
            4-USERFLOW ──(승인: 화면 목록 확정)
                                     ▼
            requirements/<기능> × N  (순서 없음)
                                     ▼
            screens/<화면> × N  (순서 없음, 디자인 문서 필요, 주석 모드로 컴포넌트 선택·그리기 수정)
                                     ▼
            changes/001-mvp
                                     ▼
            내보내기 (zip 다운로드)

  각 문서 단계: 생성 → 편집/피드백(되돌리기) → 승인  (승인 취소 → 다시 수정)
```

1. **프로젝트 생성** — 이름과 아이디어를 입력하고 디자인 문서를 붙여 넣는다. 화면 정의서 전까지만 넣으면 된다. → [requirements/project.md](requirements/project.md)
2. **인터뷰 (선택)** — 에이전트를 고르고 질문에 하나씩 답한다. 끝나면 요약을 편집·승인한다. 건너뛰면 아이디어만으로 시작한다. → [requirements/interview.md](requirements/interview.md)
3. **기본 문서·요구사항 문서** — 단계마다 에이전트를 고르고 생성한다. 직접 편집하거나 피드백으로 재생성하고, 마음에 안 들면 되돌린다. 승인하면 다음 단계가 열린다. `0-PRODUCT.md` 승인 때 요구사항 문서 목록이, `4-USERFLOW.md` 승인 때 화면 목록이 정해진다. → [requirements/documents.md](requirements/documents.md)
4. **화면 정의서** — 화면마다 HTML 목업을 생성하고, 미리보기에서 컴포넌트를 고르거나 그림을 그려 주석을 쌓은 뒤 한 번에 보내 고친다. → [requirements/screens.md](requirements/screens.md)
5. **변경 기록** — `changes/001-mvp.md`를 생성·승인한다. → [requirements/documents.md](requirements/documents.md)
6. **내보내기** — 승인된 문서 세트를 `docs/` 구조의 zip으로 내려받는다. → [requirements/export.md](requirements/export.md)

**기존 저장소에서 시작** — 새 프로젝트에 GitHub 저장소를 넣으면 클론한 코드를 기준으로 같은 흐름을 밟는다. 화면 정의서는 건너뛰고, 변경 기록은 `changes/001-baseline.md`다. 마지막에 zip 대신 PR로 올릴 수 있다. GitHub 연결은 연결 화면에서 한다. → [requirements/github.md](requirements/github.md)

앞 문서를 다시 고치려면 승인을 취소한다. 뒤 문서는 그대로 남고 "앞 문서 변경됨" 표시가 붙는다.

## 화면 간 이동

- 상단 **연결** → 간편 로그인 / 터미널 탭으로 구독 계정 연결
- 연결 → 로그인된 계정의 연결 해제 → 미로그인 상태에서 다시 연결 가능
- 상단 바는 로고 → 메뉴(**프로젝트**, **연결**) → 사용량 순서이고, 현재 메뉴에 밑줄을 표시한다. 연결 화면은 **AI 에이전트**·**GitHub** 섹션으로 나뉘며 로그인 방식 탭은 하나다 ([changes/011-connections-page.md](changes/011-connections-page.md))
- 프로젝트 목록 → 프로젝트 상세 (프로젝트 선택 또는 생성 직후)
- 프로젝트 목록 → 프로젝트 삭제 (이름 재입력 확인)
- 프로젝트 상세 안에서는 단계 목록(인터뷰 · 기본 문서 · 요구사항 문서 · 화면 정의서 · 변경 기록 · 내보내기)으로 이동한다. 생성 조건이 안 되는 단계도 열 수는 있지만 생성 버튼이 비활성이다.
- 앱을 다시 켜면 프로젝트 목록에서 이어서 진행한다. 진행 상태는 DB에 남아 있다.

## 인증·권한 분기

앱 자체 인증은 없다. 분기는 에이전트 CLI의 설치·로그인 상태 하나다.

| 상태 | 화면 |
| --- | --- |
| 선택한 CLI가 설치되고 구독으로 로그인됨 | 정상 실행 |
| CLI 미설치 | 설치·경로 설정 안내. 다른 에이전트를 고를 수 있다 |
| CLI 미로그인 | 연결 화면에서 간편 로그인 또는 실제 터미널로 구독 로그인한 뒤 다시 실행. Codex는 터미널에서 로그인해 있어도 SDDMaker용 로그인이 한 번 더 필요하다 |
| 구독이 아닌 방식(API 키 등)으로 로그인됨 | 실행하지 않고 구독 로그인 안내 |

세부 판정 방법은 [requirements/agent-cli.md](requirements/agent-cli.md#예외).

## 주요 실패·복구 경로

| 실패 | 복구 |
| --- | --- |
| 생성 도중 에이전트 실패·취소 | 기존 본문은 바뀌지 않는다. 에러를 보여 주고 다시 실행할 수 있다 |
| 피드백 재생성·주석 반영 결과가 나쁨 | 되돌리기로 직전 본문 복구 (1회분) |
| `0-PRODUCT.md`·`4-USERFLOW.md`의 링크가 규칙 위반 (`0-PRODUCT.md`는 링크 없음 포함) | 승인되지 않는다. 본문을 고치거나 피드백으로 재생성한 뒤 다시 승인 |
| 화면 정의서 단계인데 디자인 문서 없음 | 프로젝트 디자인 문서를 넣은 뒤 생성 |
| 인터뷰 답변 처리 실패 | 다시 시도 (답변은 한 번만 저장된다) |
| 인터뷰 도중 앱 종료 | 메시지와 세션 ID가 남아 있어 이어서 답할 수 있다 |
| 승인 취소 후 목록에서 빠진 문서 | 삭제한 뒤 내보낸다 |

## 두 핵심 여정 (014)

1. **기존 프로젝트** 선택 → 필수 GitHub 저장소와 선택 이름/아이디어 입력 → 연결/클론 완료 → 인터뷰 승인 또는 사용자가 명시적으로 건너뛰기 → **전체 초안 만들기** → 기본 문서·현재 PRODUCT 연결 요구사항·`changes/001-baseline.md` 순차 생성 → 초안 상태와 코드 근거/`확인 필요`·원문 비교 검토 → 수정/개별 승인 또는 확인 목록을 보고 **검토한 초안 일괄 승인** → 실제 승인 조건 충족 → PR 미리보기의 기준 SHA·덮어쓰기 목록 확인 → 명시 확인 후 PR. 화면 HTML·디자인 생성은 없다.
2. **새 프로젝트** 선택 → 필수 이름/아이디어 입력(숨겨진 저장소는 보내지 않음) → 한 질문씩 인터뷰 → 사용자·문제/사용 사례·MVP 포함·MVP 제외·우선순위/의존성·측정 가능한 성공·미확정 가정의 요약을 편집/승인 → 기존 수동 문서 흐름 → 요구사항에 연결된 구현 순서·의존성·관찰 가능한 완료 기준·제외/차단 사항을 기존 `changes/001-mvp.md`에 작성 → 검토/승인 → ZIP. 인터뷰 건너뛰기와 수동/기존 요약 승인도 유지한다.

유형 전환은 입력값을 화면에 보관하되 활성 유형의 값만 제출한다. 기존 저장 프로젝트는 저장소 유무로 여정을 판정한다. 모든 자동 생성 결과는 검토 전 초안이고 승인/PR은 사용자의 별도 행동이다. 세부 조건은 [프로젝트](requirements/project.md), [문서](requirements/documents.md), [인터뷰](requirements/interview.md), [GitHub](requirements/github.md)에 둔다.

### 배치 중단과 검토 복구

- 실행 중 현재 경로·완료/남은 개수·취소를 표시한다. 문맥을 바꾸는 조작은 잠근다. 실패 경로/오류를 표시하고 이미 저장한 초안은 유지한다.
- 실패·취소·연결 끊김·재시작 후 **남은 초안 이어 만들기**는 저장된 문서에서 작업을 다시 계산하여 비어 있는 것만 만든다. 자동 재시작은 없다. 다시 불러온 뒤 종료 원인을 추측하지 않고 부분 완료로 안내한다.
- 기존 PRODUCT 링크 오류나 `앞 문서 변경됨`이 있으면 영향 경로를 보여 주고 중단한다. 사용자가 본문을 검토하고 명시적으로 확인하거나 재생성한 뒤 재개한다. 초안의 확인은 초안 상태를 유지한다.
- 일괄 승인 전 문서 경로 확인 목록과 검토 토큰을 사용한다. 검토 뒤 변경은 `review_changed`로 재검토를 요청하고, 잘못된 문서가 있으면 어떤 문서도 부분 승인하지 않는다.
- PR 기준이 오래되면 서버는 `repo_stale`과 두 SHA를 반환하고, 화면은 현재 초안을 보존하는 복구 안내를 보여 준다. 현재 프로젝트/초안은 그대로 보존하고, 저장소로 **새 프로젝트를 만들어** 다시 생성·검토하도록 안내한다. ZIP은 실제 승인을 모두 마친 경우에만 가능하다. 원격 확인 실패에도 push하지 않으며 reset/rebase는 없다. 최종 확인 이후 push까지의 원격 변경 경쟁은 남는다.
