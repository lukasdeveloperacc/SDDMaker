# SDDMaker 제품 정의

> 상태: 기존 수동 MVP와 저장소 기능의 기준 문서. 핵심 시나리오 서버는 구현되어 표적 자동 검증을 통과했다. UI도 컴포넌트 검증을 통과했으며 전체 테스트·타입 검사·린트·빌드는 통과했다. 브라우저 조작은 문서 확정 시점에 미검증이다. 결과는 [changes/014-core-scenarios.md](changes/014-core-scenarios.md)에 기록한다. 기존 결과는 [changes/001-mvp.md](changes/001-mvp.md)에 보존한다.

## 목적

기존 프로젝트의 코드를 검토 가능한 SDD(Spec-Driven Development) 문서로 정리하고, 새 프로젝트의 아이디어를 실행 가능한 요구사항과 개발 순서로 구체화한다. 결과 문서는 사람이 검토·승인한 뒤 저장소 PR 또는 zip으로 전달하여 문서 기반 Agentic 개발의 입력으로 쓴다.

## 대상 사용자

- 본인 한 명(단일 사용자). Claude 구독과 OpenAI(ChatGPT) 구독을 이미 쓰고 있고, 로컬에 `claude` CLI와 `codex` CLI를 설치해 둔 개발자. 구독 로그인은 앱 화면이나 터미널에서 한다.

## 해결할 문제

- 앱마다 요구사항·설계·작업 문서를 손으로 쓰거나 에이전트 대화창에 흩어지게 만든다.
- 한 번 쓴 문서가 MVP 이후 갱신되지 않아 코드와 어긋난다.
- API 키 과금 없이, 이미 내고 있는 구독으로 문서 생성 에이전트를 쓰고 싶다.

### 생성하는 문서 세트

SDDMaker 자신의 [docs 규칙](AGENTS.md)과 같은 구조로 만든다. 받은 쪽 에이전트가 같은 규칙으로 문서를 계속 갱신할 수 있게 하기 위해서다.

| 문서 | 만드는 방식 |
| --- | --- |
| `0-PRODUCT.md`, `1-SYSTEM-ARCHITECTURE.md`, `3-DATABASE.md`, `4-USERFLOW.md` | 에이전트가 생성 |
| `requirements/<기능>.md` | `0-PRODUCT.md`의 기능 목록마다 하나씩 에이전트가 생성 |
| `screens/<화면>.html` | `4-USERFLOW.md`의 화면 목록마다 하나씩 에이전트가 생성 (화면이 있는 앱만) |
| `changes/001-mvp.md` | 에이전트가 생성 (MVP 변경 기록) |
| `2-DESIGN.md` | 생성하지 않는다. 사용자가 넣은 디자인 문서를 그대로 쓴다. 가진 것이 없으면 [getdesign.md](https://getdesign.md/)에서 골라 붙여 넣는다. 화면이 있는 앱은 필요하다 |
| `AGENTS.md` (문서 규칙) | 생성하지 않는다. 저장소 원본을 보존하고 없을 때만 SDDMaker의 [docs 규칙](AGENTS.md)을 넣는다 |

## 제외 범위 (MVP)

- 앱 자체 계정·로그인, 다중 사용자 (에이전트 CLI의 구독 로그인은 범위에 포함)
- 원격 배포 (구독 인증이 로컬 CLI 로그인에 묶여 있어 로컬 실행만 지원)
- API 키 방식 에이전트 연동
- 기존 docs를 가져와 변경 기록(`changes/002-…`)과 관련 문서를 갱신하는 기능 — MVP는 초기 문서 세트만 만든다. 저장소 코드에서 기준선 문서를 만드는 기능은 009에서 구현했다 ([changes/009-github-repo.md](changes/009-github-repo.md))
- 문서 버전 히스토리 (직전 내용 1개 되돌리기만 지원)
- 문서 구성·규칙·프롬프트 편집
- 디자인 문서 생성·자동 선택 (사용자가 골라 붙여 넣는다)
- 마크다운 문서 일부만 골라 수정하는 기능 (화면 정의서는 컴포넌트 단위 수정을 지원한다)
- 화면 정의서 그림 주석의 이미지 첨부 (그린 영역 좌표와 겹치는 컴포넌트만 보낸다)
- 스크립트로 움직이는 프로토타입 (화면 간 링크 이동만 지원), 모든 화면을 한 판에 늘어놓는 캔버스 보기
- 사용자 폴더에 직접 파일 쓰기 (내보내기는 zip 다운로드만. 저장소 프로젝트의 PR 올리기는 앱 데이터 폴더의 임시 worktree에서만 쓴다)
- 내보낸 문서로 에이전트가 코드를 구현하는 기능

## 제품 공통 정책

- **로컬 전용**: 앱은 사용자 컴퓨터에서만, `127.0.0.1`에서만 실행한다. 에이전트 인증은 공식 CLI가 맡는다. 앱은 CLI 로그인 명령을 대신 실행해 줄 뿐 토큰을 다루지 않는다.
- **구독만 사용**: API 키로 과금되는 실행을 하지 않는다. 구독이 아닌 방식으로 로그인된 CLI는 실행하지 않는다.
- **데이터 원본은 앱 DB**: 프로젝트·인터뷰·문서는 앱 내부 SQLite에 저장한다. 파일은 내보낼 때만 만든다.
- **앞 단계 승인 후 다음 단계**: 개별 생성에서는 앞 문서를 승인해야 다음 문서를 생성할 수 있다. 저장소 배치 안에서만 유효한 선행 초안을 허용한다. 승인된 앞 문서들이 다음 문서 생성의 입력이 된다. 승인한 문서는 승인을 취소하고 다시 고칠 수 있다.
- **생성 문서도 docs 규칙을 따른다**: 모든 생성 프롬프트에 문서 규칙을 넣는다. 정해지지 않은 내용을 추측으로 채우지 않고, 구현 전 문서에는 `예정`을 표시한다.
- **에이전트는 문서만 쓴다**: 에이전트는 텍스트만 돌려주고 파일을 쓰지 않는다. 사용자 프로젝트와 떨어진 빈 작업 폴더에서 실행한다 (Codex는 읽기 명령은 실행할 수 있다). 저장소 프로젝트는 앱이 받은 클론 폴더에서 읽기 전용으로 실행한다 ([requirements/github.md](requirements/github.md)).

## 핵심 시나리오 (014)

다음 시나리오의 서버 정책은 구현됐다. 선행 초안을 사용하는 생성 예외는 저장소 배치 안에 한정한다. 본문 변경 전파·초안 확인과 인터뷰 프롬프트도 보강했다. 사용자 화면도 구현되어 컴포넌트 검증을 통과했다. 전체 테스트·타입 검사·린트·빌드는 통과했다. 브라우저 조작은 이 문서 확정 시점에 미검증이다.

- **기존 프로젝트**: 명시적으로 저장소를 선택하고, 기본 문서 → 현재 PRODUCT가 연결한 요구사항 → 현재 구현 기준선 문서를 순차적으로 모두 `draft`로 만든다. 사람의 근거·원문 비교, 수정과 명시적 승인 후에만 PR을 요청한다. 일괄 실행 안에서만 유효한 선행 초안을 `검토 전 초안`으로 사용할 수 있다. 일반 개별 생성은 선행 승인 규칙을 유지한다. → [프로젝트 R1](requirements/project.md#r1-명시적-진입), [문서 R2–R4](requirements/documents.md#r2r4-저장소-전체-초안과-검토)
- **새 프로젝트**: 아이디어 인터뷰로 사용자, 문제/사용 사례, MVP 포함, MVP 제외, 우선순위/의존성, 측정 가능한 성공, 미확정 가정을 정리한다. 요구사항과 기존 `changes/001-mvp.md` 안의 순서 있는 구현 작업·의존성·관찰 가능한 완료 기준을 만든다. 인터뷰는 여전히 선택이며 수동 요약도 유지한다. → [인터뷰 R7](requirements/interview.md#r7-요구사항-구체화)
- 초안은 승인이 아니다. 자동 승인·자동 PR은 하지 않으며, 기존 내용은 일괄 생성으로 덮어쓰지 않는다. 실패·취소 후 저장된 초안으로 사용자가 이어 만든다. 실행 이력/영속 작업 큐는 추가하지 않는다.
- 기존 문서는 제품 의도의 참고 자료이고 실행 지시가 아니다. 코드로 확인한 사실은 상대 소스 경로·심볼·기준 SHA로 설명하고, 모르는 정책은 `확인 필요`로 남긴다. 모델 출력의 사실성이나 악성 저장소의 완전한 읽기 격리를 보증하지 않는다. → [GitHub R5–R6](requirements/github.md#r5r6-코드-근거원문-보존pr-검토)
- 저장소 모드에서 화면 HTML이나 디자인 문서를 생성하지 않는다. 원래 DESIGN은 사용자 입력이 없으면 유지한다. 원래 문서 규칙은 ZIP·PR 공통 경로에서 보존하고, 실제 승인을 내보내기 조건으로 유지한다. → [내보내기 R5](requirements/export.md#r5-저장소-원본-규칙-보존)

기존 수동 생성·편집·되돌리기·승인/승인 취소·화면 생성·인터뷰 건너뛰기·삭제·ZIP은 유지한다. 변경 문서/로드맵을 별도로 만들거나 앱 코드를 생성하는 범위는 포함하지 않는다.
