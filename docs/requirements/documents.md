# 문서 생성·편집·승인

> 상태: 기존 수동 흐름을 유지하며 014 서버 기능은 구현되어 표적 자동 검증을 통과했다. UI는 구현되어 컴포넌트 검증을 통과했고 전체 테스트·타입 검사·린트·빌드는 통과했다. 브라우저 조작은 문서 확정 시점에 미검증이다 ([014](../changes/014-core-scenarios.md)). 기존 결과는 [001](../changes/001-mvp.md)에 보존한다.

## 목적

[문서 세트](../0-PRODUCT.md#생성하는-문서-세트)를 정해진 순서로 하나씩 만들고, 사용자가 다듬어 승인한 문서를 다음 문서의 입력으로 쓴다. 화면 정의서도 이 규칙을 따르고, 다른 점은 [screens.md](screens.md)에 둔다.

## 생성 순서

| 순서 | 문서 (경로) | 생성 조건 |
| --- | --- | --- |
| 1 | `0-PRODUCT.md` | 인터뷰가 `approved` 또는 `skipped` |
| 2 | `1-SYSTEM-ARCHITECTURE.md` | `0-PRODUCT.md` 승인 |
| 3 | `3-DATABASE.md` | `1-SYSTEM-ARCHITECTURE.md` 승인 |
| 4 | `4-USERFLOW.md` | `3-DATABASE.md` 승인 |
| 5 | `requirements/<기능>.md` (기능마다) | `4-USERFLOW.md` 승인. 요구사항 문서끼리는 순서 없음 |
| 6 | `screens/<화면>.html` (화면마다) | 모든 요구사항 문서 승인 + 디자인 문서 있음 (디자인 단계에서 붙여 넣거나 만든다, [screens.md](screens.md#디자인-단계)). 화면끼리는 순서 없음. 화면이 없으면 건너뜀 |
| 7 | `changes/001-mvp.md` | 모든 요구사항 문서와 화면 정의서 승인 |

"모든 요구사항 문서·화면 정의서"에서 [목록에서 빠짐](#목록-확정) 문서는 제외한다.

저장소 프로젝트의 7단계는 `changes/001-baseline.md`다. 화면(6단계)은 `4-USERFLOW.md`에 화면 링크가 있을 때만 있고, 일괄 초안은 만들지 않는다 ([github.md](github.md#저장소-프로젝트의-생성)).

`AGENTS.md`는 생성하지 않는다. `2-DESIGN.md`는 문서 행이 아니라 디자인 단계에서 만들어 프로젝트에 저장한다 ([screens.md](screens.md#디자인-단계), [0-PRODUCT.md](../0-PRODUCT.md#생성하는-문서-세트)). 아래에서 "기본 문서"는 `0-PRODUCT.md`, `1-SYSTEM-ARCHITECTURE.md`, `3-DATABASE.md`, `4-USERFLOW.md`를 말한다.

## 동작

- **실행 설정**: 에이전트(`claude` | `codex`)·모델·추론 강도 선택은 연결 화면의 **기본 실행 설정**에 있고, 프로젝트 작업 화면 상단의 접힌 **실행 설정**에서 같은 값을 바꿔 실행할 수 있다(바꾼 값은 다음 기본값이 된다). 인터뷰·문서·화면·일괄 생성이 모두 이것으로 실행한다. 고른 에이전트와 에이전트별 모델·강도는 브라우저에 남는다. 실행이 도는 동안은 바꿀 수 없고, 진행 중인 인터뷰 화면에서는 에이전트가 시작한 에이전트로 고정된다(모델·강도는 바꿀 수 있다).
- **생성**: 실행 설정의 에이전트로 생성한다. 결과가 스트리밍으로 보이고(Codex는 끝날 때 한 번에), 끝나면 `draft`로 저장된다.
- **직접 편집**: 편집기에서 수정하고 저장한다. `empty` 문서를 직접 써서 저장해도 `draft`가 된다. 편집기는 **마크다운 / 미리 보기** 탭으로 나뉘어 한 번에 한 쪽만 보인다. 처음에는 본문이 있거나 읽기 전용이면 미리 보기, 본문이 비어 있고 편집할 수 있으면 마크다운 탭이 열린다. 탭을 바꿔도 입력 내용은 유지되고, 방향키·Home·End로 탭을 옮길 수 있다. 승인된 문서도 같은 탭으로(읽기 전용) 보인다. 저장소 프로젝트에서 같은 경로의 원본 항목이 있으면 탭 줄 끝에 **저장소 원본** 탭이 붙어 기준 커밋과 원문(또는 제외 이유)을 보여 주며, 본문이 없는 문서는 탭 없이 아래에 따로 보여 준다. 본문 속 상대 링크(`requirements/<이름>.md`, `../0-PRODUCT.md`)는 주소로 이동하지 않고 같은 프로젝트의 그 문서로 이동하며, 프로젝트에 없는 문서면 안내를 보여 준다. 인터뷰 요약 편집기도 같은 탭을 쓴다([interview.md](interview.md)). 화면 정의서의 HTML 편집기는 그대로다 ([changes/012-editor-tabs.md](../changes/012-editor-tabs.md)).
- **피드백 재생성**: 피드백을 입력하면 현재 본문(직접 수정 포함)과 피드백을 에이전트에 넘겨 **문서 전체**를 다시 받아 교체한다.
- **되돌리기**: 마지막 생성·재생성 직전 본문으로 복구한다. 1회분만 보관한다.
- **승인**: `approved`가 되고 다음 단계의 생성이 가능해진다.
- **승인 취소**: `approved` 문서를 다시 고치려면 승인을 취소해 `draft`로 돌린다. 뒤 단계 문서는 그대로 두고 [앞 문서 변경 표시](#앞-문서-변경-표시)를 붙인다.

## 목록 확정

`0-PRODUCT.md` 승인 시 요구사항 문서 목록을, `4-USERFLOW.md` 승인 시 화면 목록을 본문 링크에서 뽑는다.

- 마크다운 링크의 대상이 `requirements/<이름>.md`(화면은 `screens/<이름>.html`)인 것만 센다. 앞의 `./`와 뒤의 `#앵커`는 허용하고, 중복은 하나로 친다.
- 코드 블록·인라인 코드 안의 링크는 세지 않는다 (마크다운 파서의 링크만 센다).
- 이름은 영문 소문자·숫자·`-`만 쓴다.
- 요구사항 이름 `agents`, `claude`는 쓸 수 없다. 대소문자를 구분하지 않는 파일 시스템(macOS 기본)에서 에이전트 지시 파일 `AGENTS.md`, `CLAUDE.md`로 읽힌다.
- 승인 화면에 뽑아낸 목록을 보여 준다. 목록을 바꾸려면 본문을 고친다.
- `0-PRODUCT.md`에 요구사항 링크가 하나도 없거나, 이름 규칙에 어긋나면 승인할 수 없고 이유를 표시한다. 화면 링크가 없으면 화면 정의서 단계를 건너뛴다.
- 다시 승인할 때: 새로 생긴 링크는 문서를 `empty`로 추가한다. 빠진 링크의 문서는 남기고 "목록에서 빠짐"으로 표시한다. 이 문서는 삭제 버튼이 생기고, 삭제하기 전까지 내보낼 수 없다.

## 앞 문서 변경 표시

- 승인 취소 또는 PUT·되돌리기·재생성으로 실제 본문이 바뀌면 생성 순서상 뒤 문서 중 본문이 있는 문서에 "앞 문서 변경됨" 표시를 붙인다. 동일 본문 저장은 표시를 세우지 않는다.
- **앞 문서 변경 반영**(동기화): 표시가 붙은 요구사항·화면 정의서를 현재 본문 기준으로 한 번에 갱신한다. 요구사항을 먼저(동시 3개) 고친 뒤, 그 결과로 표시가 붙은 화면을 고친다. 앞 문서와 어긋나는 부분만 고치게 하고, 다시 쓴 문서는 초안이 되며(승인 해제) 직전 본문은 되돌리기로 남는다. 에이전트는 문서마다 앞 문서와 어긋나는지 검사해, 고칠 곳이 없으면 `변경 없음`만 답하고 그 문서는 내용과 승인 상태를 그대로 둔 채 표시만 지운다(검사와 갱신이 호출 한 번이다). 요구사항을 갱신하려면 기본 문서 4개가 모두 승인돼 있어야 한다. **자동 실행**: 기본 문서가 모두 승인돼 있고 표시된 문서가 있으면 프로젝트 화면이 알아서 실행한다(문서마다 자동 시도는 한 번, 실패한 문서는 버튼으로 다시). 사이드바 체크박스로 끌 수 있고(브라우저에 저장, 기본 켜짐) 끄면 버튼으로만 실행한다. 실행 중 직접 고친 문서는 덮어쓰지 않고, 일부가 실패해도 나머지는 저장하며 실패 목록을 준다. 화면 결과에 스크립트·이벤트 속성이 있으면 저장하지 않는다. 변경 기록은 대상이 아니다(직접 확인). 사이드바의 **앞 문서 변경 반영 · N개** 버튼이 실행한다.
- 표시가 붙어도 상태(`draft`/`approved`)는 바뀌지 않는다. 사용자가 그 문서를 다시 생성하거나, 승인하거나, `draft`/`approved`에서 **확인**(상태 유지, 표시만 지움)을 요청하면 표시가 사라진다.
- 화면 정의서는 생성·피드백 재생성 결과를 저장할 때(`PUT`에 `keepUndo: true`와 `generatedBy`) 같은 방식으로 표시를 지운다. 직접 편집 저장은 표시를 지우지 않는다.
- 생성 조건은 그대로 적용한다. 예: `0-PRODUCT.md` 승인을 취소하면 다시 승인할 때까지 `1-SYSTEM-ARCHITECTURE.md`를 생성·승인할 수 없다.

## 생성 입력

모든 문서: 문서별 고정 프롬프트 + 문서 규칙(`AGENTS.md`) + 아이디어 + 승인된 인터뷰 요약(있으면) + 디자인 문서(있으면) + 승인된 앞 문서 전부.

- `requirements/<기능>.md`: 기본 문서까지만 넣고 다른 요구사항 문서는 넣지 않는다. 대상 기능 이름을 함께 넣는다.
- `screens/<화면>.html`: [screens.md](screens.md#생성). 승인된 다른 화면 하나(기준 화면)도 넣는다.
- `changes/001-mvp.md`: 승인된 마크다운 문서 전부와 화면 파일 목록을 넣는다 (화면 HTML 본문은 넣지 않는다).
- 피드백 재생성이면 현재 본문과 피드백을 더한다.

단계 간 맥락은 CLI 세션이 아니라 이 입력으로 넘긴다. 그래서 단계마다 다른 에이전트를 써도 된다.

## 출력 규칙

- 모든 프롬프트는 "문서 본문만 출력한다(서두·맺음말 없음)"를 지시한다.
- 응답 전체가 코드 울타리 하나(```` ``` ````, ```` ```markdown ````)로 감싸져 있으면 울타리를 벗기고 저장한다.
- `0-PRODUCT.md` 프롬프트는 기능마다 `[기능 이름](requirements/<기능>.md)` 링크를 넣고 이름 규칙을 지키게 한다.
- `4-USERFLOW.md` 프롬프트는 화면마다 `[화면 이름](screens/<화면>.html)` 링크를 넣게 한다.
- 새 프로젝트의 구현 전 문서는 `예정`을 표시하게 한다. 저장소 문서는 코드로 확인된 현재 동작을 `구현됨`으로 쓰고 모르는 의도는 `확인 필요`로 남긴다 ([AGENTS.md](../AGENTS.md)).
- 디자인 문서가 없는 프로젝트는 `2-DESIGN.md`를 링크하지 않게 한다.

## 규칙

- **생성 조건**: 위 조건이 안 되면 생성·승인 버튼이 비활성이고, API는 409를 돌려준다.
- **동시 실행**: 한 프로젝트에서 에이전트 실행(인터뷰·생성·화면 주석)은 한 번에 하나만 돈다. 구독 사용량 한도를 아끼고 앞뒤 문서 충돌을 막기 위해서다. 실행 중 다른 실행 요청은 409. 예외로 요구사항 문서끼리, 화면 정의서끼리는 서로 입력이 겹치지 않아, 하나씩 따로 생성하는 것도 같은 잠금을 공유해 동시에 3개까지 돈다(3개째까지 허용, 넘으면 409). 같은 문서의 중복 생성은 막는다.
- **요구사항 한 번에 만들기** (새 프로젝트): 요구사항 문서는 입력이 겹치지 않아(기본 문서만 본다) 비어 있는 것을 동시에 3개까지 만든다. 실행 잠금은 하나만 잡고(`requirements`) CLI를 여러 개 띄우며, 문서마다 끝나는 대로 초안으로 저장한다. 그 사이 직접 쓴 문서는 덮어쓰지 않고, 일부가 실패해도 나머지는 저장하며 실패 목록을 준다. `POST /api/projects/:id/requirements/generate`.
- **화면을 떠나도 이어짐**: 마크다운·화면 정의서 생성과 요구사항 한 번에 만들기는 서버가 저장하므로 연결이 끊겨도(화면 이동·새로고침) 끝까지 간다. 취소는 `DELETE /api/projects/:id/run`(204)만 한다. 진행은 `GET /api/projects/:id`의 `running`(`progress`: 전체·완료·진행 중·실패 경로)으로 읽고, 화면은 단계 목록의 움직이는 **생성 중** 배지로 보여 준다(상단 배너는 없다). 상태 변화는 `GET /api/projects/:id/events`(SSE: `ready`·`change`·`ping`)가 알리면 화면이 상세를 다시 읽어 실시간으로 반영한다. 화면 정의서 생성도 서버가 저장하므로 같다. 브라우저가 저장하는 디자인 문서 생성과 화면 주석 반영은 화면을 떠나면 중단된다.
- **실행 중 잠금**: 실행 중인 문서의 저장·되돌리기·승인·승인 취소는 409.
- **승인 문서 잠금**: `approved` 문서의 저장·생성·되돌리기는 409. 승인 취소부터 한다.
- **되돌리기 보관**: 본문이 있는 문서를 생성·재생성으로 교체할 때 교체 전 본문을 `previous_content`에 저장한다. 직접 편집 저장은 `previous_content`를 바꾸지 않는다. 되돌리면 `previous_content`를 비운다. 화면 정의서는 저장 요청의 `keepUndo`로 같은 일을 한다.
- **승인 조건**: 본문이 비어 있으면 승인할 수 없다.

## 화면 상태

| 상태 | 표시 |
| --- | --- |
| `empty` | 생성 버튼 (생성 조건이 안 되면 비활성과 이유), 직접 쓰기 |
| 실행 중 | 스트리밍 본문(Codex는 "생성 중"), 취소 버튼, 다른 조작 비활성 |
| `draft` | 편집기·미리보기, 피드백 입력, 되돌리기(가능할 때), 승인 버튼 |
| `approved` | 승인 표시, 승인 취소 버튼, 다음 단계로 이동 |
| 앞 문서 변경됨 | 위 상태에 덧붙는 표시. 초안/승인본 모두 명시적 확인 버튼으로 상태를 유지하고 표시만 제거 |
| 목록에서 빠짐 | 위 상태에 덧붙는 표시 + 삭제 버튼 |

요구사항 문서와 화면 정의서는 각각 목록으로 보여 주고, 문서마다 위 상태를 따른다. 시각 기준은 [2-DESIGN.md](../2-DESIGN.md).

## API

`:path`는 URL 인코딩한 문서 경로다 (예: `requirements%2Fproject.md`). SSE 이벤트는 [agent-cli.md](agent-cli.md#sse-이벤트-예정).

| 메서드·경로 | 요청 | 응답 |
| --- | --- | --- |
| `POST /api/projects/:id/documents/:path/generate` | `{ agent, feedback? }` | SSE — 생성 본문. 마크다운·화면 정의서 모두 서버가 저장(화면을 떠나도 이어짐) |
| `PUT /api/projects/:id/documents/:path` | `{ content, keepUndo?, generatedBy? }` | 저장된 문서. `empty`면 `draft`로 바뀐다. `keepUndo`는 화면 정의서 전용. `generatedBy`(에이전트 이름)는 화면 정의서 생성·재생성 저장 전용이며 `keepUndo`와 함께 보낸다. 있으면 생성 에이전트를 기록하고 "앞 문서 변경됨"을 지운다 |
| `POST /api/projects/:id/documents/:path/undo` | — | 복구된 문서 |
| `POST /api/projects/:id/documents/:path/approve` | — | `approved` 문서. `0-PRODUCT.md`면 요구사항 목록, `4-USERFLOW.md`면 화면 목록 포함 |

| `POST /api/projects/:id/sync` | `{ agent }` | SSE — `done.text`는 `{ done, unchanged, failed }` JSON(`unchanged`는 고칠 곳이 없어 표시만 지운 문서). 서버가 문서마다 저장(연결이 끊겨도 이어짐), 취소는 `DELETE /run`. 반영할 문서가 없으면 409 `precondition` |
| `POST /api/projects/:id/documents/:path/acknowledge` | — | "앞 문서 변경됨" 표시를 지운 문서 (상태 유지) |

## 완료·테스트 기준

- [ ] Codex로 `0-PRODUCT.md` 생성 → 직접 수정 → 피드백 재생성 → 되돌리기 → 승인이 된다.
- [ ] `0-PRODUCT.md` 승인 시 본문의 요구사항 링크대로 요구사항 문서가 `empty`로 생긴다. 링크가 없거나 `agents`·`claude`면 승인되지 않는다.
- [ ] 같은 방식으로 `1` → `3` → `4`(화면 목록 확정) → 요구사항 문서들 → 화면 정의서들 → `changes/001-mvp.md`까지 승인된다.
- [ ] 생성 조건이 안 되는 문서는 생성·승인할 수 없다 (UI 비활성, API 409).
- [ ] 한 실행이 도는 동안 같은 프로젝트의 다른 실행 요청은 409.
- [ ] 승인된 `0-PRODUCT.md`의 승인을 취소하면 뒤 문서에 "앞 문서 변경됨"이 붙고, 링크를 하나 지우고 하나 더해 다시 승인하면 새 문서가 생기고 지운 문서는 "목록에서 빠짐"이 된다.
- [ ] 생성이 실패하거나 취소돼도 기존 본문이 남는다.
- [ ] 응답이 코드 울타리로 감싸져 와도 울타리 없이 저장된다.
- [ ] 단계마다 다른 에이전트를 골라도 앞 문서 내용이 다음 문서에 반영된다.
- [ ] 생성된 문서가 문서 규칙을 따른다 — 구현 전 `예정` 표시, 기능 상세는 요구사항 문서로 링크.

## R2–R4 저장소 전체 초안과 검토

서버 배치·보존·승인과 버튼·확인 목록·진행/비교 화면은 구현되어 표적 자동/컴포넌트 검증을 통과했다. 전체 테스트·타입 검사·린트·빌드는 통과했다. 브라우저 조작은 이 문서 확정 시점에 미검증이다.

일괄 생성·일괄 승인은 저장소 프로젝트에만 적용한다. R3의 본문 변경 전파·명시적 초안 확인 확장은 일반 문서에도 적용한다. 기존 개별 생성의 선행 **승인** 조건, 편집·피드백·되돌리기·승인/승인 취소·화면 생성·목록에서 빠진 문서의 삭제/내보내기 정책은 유지한다. 일괄 생성으로 승인 조건을 우회하지 않는다.

### R2 순차 초안과 활성 목록

- **전체 초안 만들기** / **남은 초안 이어 만들기**는 인터뷰가 `approved` 또는 사용자가 명시적으로 `skipped`인 경우에만 시작한다. 활성 인터뷰를 자동 승인·폐기·건너뛰기 하지 않는다.
- 순서는 PRODUCT → ARCHITECTURE → DATABASE → USERFLOW → PRODUCT가 연결한 요구사항(경로 정렬) → `changes/001-baseline.md`다. 화면 HTML·디자인 문서는 생성하지 않는다.
- 배치 내부에서만 유효하고 비어 있지 않은 앞 문서의 초안을 `검토 전 초안`으로 표시해 입력으로 쓴다. PRODUCT는 유효한 요구사항 링크가 최소 하나 있어야 한다. PRODUCT 승인 없이도 배치 문맥에서 해당 요구사항 행을 확장할 수 있다.
- PRODUCT의 **현재 유효 본문**이 초안이든 승인본이든 같은 활성 요구사항 집합을 행 확장·선행 입력 선택·요구사항 작업 목록·기준선 입력에 쓴다. 승인본 전용 목록 계산을 배치 입력 선택에 쓰지 않는다. 이전 링크의 행은 보관하지만 배치 문맥/기준선에서 제외하며, 기존 수동 목록/내보내기 의미는 유지한다.

### R3 내용 보존과 복구

- 이미 본문이 비어 있지 않은 문서는 초안/승인본 모두 건너뛴다. 사용자가 고친 내용을 암묵적으로 재생성하지 않는다. 기존 수동 편집·승인 취소·되돌리기·재생성으로만 바꾼다.
- 유효한 문서 하나가 완료될 때마다 원자적으로 초안을 저장한다. 실패·빈 출력·잘못된 링크 출력은 해당 문서의 기존 본문을 보존한다. 취소·연결 끊김은 활성 CLI를 중단하고 부분 토큰 출력을 저장하지 않는다. 이전 완료 초안은 남는다.
- 상위 문서 PUT·되돌리기·재생성이 실제 본문을 바꾸면 본문이 있는 뒤 문서에 `upstreamChanged`를 같은 변경 단위로 세운다. 배치 초안도 포함하며 동일 본문 저장은 세우지 않는다.
- 재개 전에 보존 PRODUCT의 링크와 보존된 입력/하위 초안의 상위 변경 표시를 검증한다. 표시가 있으면 `precondition` 409와 영향 경로를 알리고 중단한다. 사용자가 검토 후 **확인**하거나 재생성하기 전에는 오래된 내용을 조용히 재사용하거나 표시를 지우지 않는다.
- 명시적 확인 API는 표시 있는 `draft`와 `approved` 모두에서 표시만 지운다. 본문과 상태를 유지하며 초안을 승인하지 않는다. 일괄 실행 중에는 확인도 `busy`다.
- 재개는 현재 저장 문서에서 남은 일을 다시 계산한다. 서버 재시작 후 살아 있는 잠금이나 자동 재개는 없고, 저장된 완료 초안으로 부분 진행을 표시한다. 영속 작업/실행 이력은 만들지 않는다. 다시 불러온 뒤 프로세스 종료와 이전 취소를 구별한다고 주장하지 않는다.

### R4 검토와 원자적 승인

- 문서별 초안/승인, 완료/남은 개수, 현재/실패 경로, 코드 근거·미확정 사항, 원문 가용성/비교를 보여 준다. [근거/원문 정책 R5](github.md#r5r6-코드-근거원문-보존pr-검토)를 따른다.
- 사용자가 **검토한 초안 일괄 승인**을 누르고 확인 목록을 본 뒤 명시적으로 승인한다. 생성과 승인은 별도이며 자동 승인은 없다. 개별 승인도 유지한다.
- 검토 토큰은 적용 대상 문서의 본문/상태/상위 변경 표시, 인터뷰 상태/요약과 디자인 본문을 반영한다. 검토 후 바뀌면 `review_changed` 409다. 상위 변경 표시는 자동 확인하지 않고 `precondition/items`로 거절한다.
- 기존 검증으로 단계 순서대로 한 트랜잭션에서 승인한다. 누락/빈 본문/잘못된 링크/오래된 입력은 전체를 거절하며 일부 문서만 승인하지 않는다. 잠금을 먼저 얻고 스냅샷을 읽되 일괄 승인 자신의 잠금을 검증 실패로 취급하지 않는다. ZIP/PR은 여전히 실제 승인을 요구한다.
- 배치 실행 중 생성 입력을 바꾸는 **모든 문서**의 저장·되돌리기·승인·승인 취소·확인·주석·삭제, 디자인/인터뷰 변경은 `busy` 409다. 잠금 획득 후 입력을 읽으며, 비동기 요청 파싱 뒤 실제 쓰기 때도 검사한다. 프로젝트 삭제는 기존 취소 후 종료 대기를 유지하고, 배치가 없으면 기존 수동 동시 실행 정책을 유지한다.

### 배치 API

계약 기준: [`src/lib/contract.ts`](../../src/lib/contract.ts). `RunKind`에 `batch`를 더하고 일반 `RunEvent`는 유지한다.

| 메서드·경로 | 요청 | 응답/조건 |
| --- | --- | --- |
| `POST /api/projects/:id/batch` | `{ agent }` | 사전 검증 후 SSE 200. 없음 404, 잘못된 요청/agent 400, 비저장소/인터뷰/상위 변경 조건은 `precondition` 409, 보존 PRODUCT/USERFLOW 링크 오류는 `invalid_links` 409, 실행 중 `busy` 409 |
| `DELETE /api/projects/:id/batch` | — | 배치만 취소하고 잠금 해제 대기. 유휴/종료 204, 다른 종류 실행 또는 아직 종료 중 `busy` 409, 없음 404. 인터뷰/PR을 취소하지 않는다 |
| `POST /api/projects/:id/batch/approve` | `{ reviewToken: string }` | 200 `{ approved: string[] }`, 토큰 누락/비문자열 `invalid_input` 400, 문자열 토큰 불일치 `review_changed` 409, 기존 검증 오류·`busy` 409. 부분 커밋 없음 |
| `GET /api/projects/:id` | — | 기존 상세 + `batch: BatchView | null`. 재조회로 진행/검토 토큰 갱신 |

`BatchView = { state: 'idle'|'running'|'completed'|'partial', currentPath: string|null, completedPaths: string[], remainingPaths: string[], error: {code: AgentErrorCode|'invalid_links', message: string, path?: string}|null, reviewToken: string }`.

SSE는 별도 `BatchEvent`를 사용한다. `progress`와 `done`은 `{ batch: BatchView }`, `delta`는 `{ path, text }`, `error`는 `{ code: AgentErrorCode|'invalid_links', message, path? }`다. 완료 문서를 먼저 저장한 뒤 이벤트를 보낸다. 사전 검증 오류는 일반 JSON 오류다. 오류/실패 경로는 서버 세션의 메모리 맵에도 남을 수 있다. 재조회 상태는 현재 저장 문서/런타임에서 계산하고, 재시작 후에는 저장된 진행만 남는다. 실패/취소/프로세스 종료의 영속 이력으로 취급하지 않는다.

### R2–R4 수용 기준 (통합 검증 기준)

- [ ] 전체 순서가 초안으로 끝나며 새 승인은 0건이고 화면/디자인을 만들지 않는다. 수동 선행 승인 조건은 그대로다.
- [ ] PRODUCT 링크를 변경하면 행 확장·입력·작업·기준선이 같은 새 활성 집합만 쓰고 이전 행은 보존한다.
- [ ] 중간 실패·빈/잘못된 출력·취소·저장 직전 취소·연결 끊김·재시작에서 완료 초안/기존 편집을 보존하고 남은 것만 재개한다.
- [ ] PUT/되돌리기/재생성 본문 변경은 뒤 초안에도 표시하고 no-op은 표시하지 않는다. 재개가 오래된 초안을 거절하고 명시적 확인은 상태를 유지한다.
- [ ] 일괄 승인은 사용자 확인과 유효 토큰을 요구하고 잘못된 문서/상위 변경/변경된 토큰에는 부분 승인하지 않는다.
- [ ] 중복 시작과 실행 입력 변경은 서비스/라우트 쓰기 경계에서도 거절하며 배치 취소가 인터뷰/PR에 영향을 주지 않는다.

서버 표적 검증 결과는 [014 검증 결과](../changes/014-core-scenarios.md#검증-방법과-결과)에 기록한다. 체크리스트는 수용 기준이며 자동 검증 결과와 브라우저 관찰을 구분한다. 브라우저·독립 검토 결과는 별도 실행 증거로 관리한다.
