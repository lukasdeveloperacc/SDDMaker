# 프로젝트

> 상태: 기존 수동 흐름을 유지하며 014 서버 기능은 구현되어 표적 자동 검증을 통과했다. UI는 구현되어 컴포넌트 검증을 통과했고 전체 테스트·타입 검사·린트·빌드는 통과했다. 브라우저 조작은 문서 확정 시점에 미검증이다 ([014](../changes/014-core-scenarios.md)). 기존 결과는 [001](../changes/001-mvp.md)에 보존한다.

## 목적

SDD 문서를 만들 앱 하나를 프로젝트로 등록하고, 진행 상태를 앱을 껐다 켜도 이어 갈 수 있게 한다.

## 동작

- **목록**: 프로젝트 이름, 생성 시각, 진행 상태(인터뷰 상태, 승인된 문서 수 / 전체 문서 수)를 보여 준다.
- **생성**: 이름과 아이디어를 입력하면 프로젝트와 기본 행 5개(기본 문서 4개 + `changes/001-mvp.md`)를 `empty`로 만들고 프로젝트 상세로 이동한다 ([3-DATABASE.md](../3-DATABASE.md#documents)). 저장소 프로젝트는 `001-mvp.md` 대신 `changes/001-baseline.md`다 ([github.md](github.md#저장소-프로젝트의-생성)).
- **GitHub 저장소**: 생성 시 저장소를 넣으면 클론한 코드를 기준으로 문서를 만든다. 이때 아이디어는 선택이다 ([github.md](github.md#저장소에서-프로젝트-만들기)).
- **디자인 문서**: 생성 시 `DESIGN.md` 마크다운을 붙여 넣는다. 프로젝트 상세 상단에는 디자인 카드를 두지 않는다. 디자인 문서가 없으면 화면 정의서 생성 단계에서만 입력란을 제공한다.
  - 가진 디자인 문서가 없으면 [getdesign.md](https://getdesign.md/)에서 만들 앱에 가장 가까운 것 하나를 골라 그 `DESIGN.md`를 복사해 붙여 넣는다. 입력란 옆에 이 링크와 안내를 보여 준다. 앱이 사이트에서 가져오거나 대신 고르지 않는다.
  - 생성 입력과 `2-DESIGN.md` 내보내기에 그대로 쓰며, SDDMaker가 고치지 않는다.
  - 화면 정의서를 만들기 전까지는 넣어야 한다 ([screens.md](screens.md#생성)). 화면이 없는 앱은 없어도 된다.
- **상세**: 단계 목록(인터뷰 · 기본 문서 · 요구사항 문서 · 화면 정의서 · 변경 기록 · 내보내기)을 보여 준다. 화면 공통 기준은 [2-DESIGN.md](../2-DESIGN.md).
- **삭제**: 확인 창에서 프로젝트 이름을 다시 입력하면 프로젝트와 인터뷰·문서를 모두 지운다. 실행 중인 에이전트가 있으면 먼저 종료한다.

## 규칙

- 저장소 없는 프로젝트의 이름과 아이디어는 공백만으로 채울 수 없다. 저장소 프로젝트는 이름·아이디어가 선택이며 이름 생략 시 저장소 이름을 쓴다.
- 디자인 문서를 바꾸면 이후 생성부터 반영된다. 이미 만든 문서는 그대로다.
- 화면 정의서 행이 있으면 디자인 문서를 비울 수 없다 (409). 바꾸는 것은 된다.
- 삭제는 되돌릴 수 없다.

## 예외

| 상황 | 처리 |
| --- | --- |
| 저장소 없는 프로젝트의 이름·아이디어 비어 있음 | 400, 화면에서 입력 오류 표시 |
| 삭제 확인 이름 불일치 | 삭제 버튼 비활성 |
| 없는 프로젝트 ID | 404 |

## API

| 메서드·경로 | 요청 | 응답 |
| --- | --- | --- |
| `GET /api/projects` | — | 프로젝트 목록 + 진행 상태 |
| `POST /api/projects` | `{ name?, idea?, designMd?, repo?, mode? }` | 201 `{ project }`. `mode` 조건은 아래 R1 |
| `GET /api/projects/:id` | — | 프로젝트, 인터뷰(메시지 포함), 문서 목록, `batch`, `repoContext`, 실행/내보내기 상태 |
| `PUT /api/projects/:id/design` | `{ designMd }` | 저장된 디자인 문서 (빈 값이면 제거) |
| `DELETE /api/projects/:id` | — | 204 |

## 완료·테스트 기준

- [ ] 프로젝트를 만들면 목록에 나타나고, 기본 행 5개가 `empty`로 생긴다.
- [ ] 디자인 문서 입력란 옆에 getdesign.md 링크가 있고, 붙여 넣은 내용이 그대로 저장된다.
- [ ] 앱을 재시작해도 프로젝트, 인터뷰 기록, 문서 본문, 승인 상태가 그대로다.
- [ ] 저장소 없는 프로젝트는 빈 이름·아이디어로 만들 수 없다.
- [ ] 프로젝트를 삭제하면 목록과 DB에서 인터뷰·문서까지 사라지고, 실행 중이던 CLI 프로세스가 남지 않는다.

## R1 명시적 진입

서버 계약과 생성 화면의 유형 선택/전환 UX는 구현되어 표적 자동/컴포넌트 검증을 통과했다. 전체 테스트·타입 검사·린트·빌드는 통과했다. 브라우저 조작은 이 문서 확정 시점에 미검증이다.

- 생성 화면은 한국어 **기존 프로젝트** / **새 프로젝트**를 명시적으로 선택하게 한다. 기존 프로젝트는 GitHub 저장소가 필수이고 이름/아이디어는 선택이다. 새 프로젝트는 이름/아이디어가 필수이며 저장소를 제출하지 않는다. 연결 오류·클론 실패는 입력/연결 단계에서 설명하고 반쪽 프로젝트를 남기지 않는다.
- 입력 검증 오류는 로컬 필수값 검사와 서버의 필드 오류 모두 해당 입력의 `aria-invalid`와 `aria-describedby`로 연결한다. 기존 도움말 ID를 유지하면서 오류 설명 ID를 추가하고, 제출 실패 후에는 현재 유형에서 첫 번째 오류 입력으로 포커스를 옮겨 키보드·보조 기술 사용자가 오류 위치와 내용을 확인할 수 있게 한다.
- 유형 전환 시 사용자가 쓴 값은 화면 안에 유지하되 비활성 유형의 저장소를 숨겨 제출하지 않는다. 새 프로젝트의 디자인 입력과 기존 수동 흐름은 유지한다.
- `POST /api/projects`의 `mode?: 'existing' | 'new'`는 선택 필드다. 명시한 `existing`에 저장소가 없거나 `new`에 저장소가 있으면 `invalid_input` 400이다. 잘못된 mode 값도 400이다. 필드를 생략한 기존 클라이언트는 저장소 유무의 종전 추론을 유지한다. 저장된 프로젝트는 `repo`로 유형을 판단하고 DB mode 열/마이그레이션은 만들지 않는다.
- 상세 `GET /api/projects/:id`는 기존 응답에 `batch: BatchView | null`, `repoContext: RepoContext | null`을 더한다. 별도 폴링 API 없이 상세 재조회로 다른 탭의 실행/종료 후 진행을 갱신한다. 비저장소 프로젝트는 두 필드가 `null`이다. 저장소라도 클론 문맥 조회가 실패하면 `repoContext`는 `null`이며, 이를 원문 부재로 꾸미지 않는다. 정확한 형태의 기준은 [`src/lib/contract.ts`](../../src/lib/contract.ts)이며 [문서 배치 API](documents.md#배치-api), [GitHub 원문 계약](github.md#원문-비교-api)을 따른다.

### R1 수용 기준 (통합 검증 기준)

- [ ] 두 유형의 필수/선택 필드, 전환 값 보존과 비활성 저장소 미제출을 확인한다.
- [ ] 키보드로 빈 새 프로젝트/빈 기존 저장소를 제출하거나 서버 필드 오류를 받으면 첫 오류 입력에 포커스가 간다. `aria-invalid`와 실제 오류 설명의 `aria-describedby` 연결, 기존 도움말 ID 보존을 확인한다.
- [ ] mode 불일치/형식 오류 400, 기존 no-mode 요청과 기존 저장 프로젝트 호환을 확인한다.
- [ ] 연결·저장소 오류가 설명되고 프로젝트/임시 클론이 남지 않는다. 기존 디자인·삭제 경로는 유지된다.

서버 표적 검증 결과는 [014 검증 결과](../changes/014-core-scenarios.md#검증-방법과-결과)에 기록한다. 체크리스트는 수용 기준이며 자동 검증 결과와 브라우저 관찰을 구분한다. 브라우저·독립 검토 결과는 별도 실행 증거로 관리한다.
